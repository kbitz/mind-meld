## Key header creation and join (Track 89A, load-bearing)

`mm-crypto-init` has **one writer**: `initflow._bootstrap_new_fleet` through `crypto.bootstrap_crypto_init` (`put_exclusive`). Both `mm init --new-fleet` and an interactive `new` answer reach it only when the folder is absent or its top level holds nothing but `.stfolder`, `.stignore`, `.stversions` and `.DS_Store`. `_classify_folder` is the one classifier: bookkeeping, in-flight (`.syncthing.*`, `~syncthing~*`), fleet (`data/`, `manifests/`, `devices/`, `syncthing/`, `retired/`, any `mm-crypto-init` spelling) and other. Anything but bookkeeping refuses with exit 1 and writes nothing; the check repeats immediately before bootstrap, and a `put_exclusive` collision (`EEXIST`, or a header already present) refuses instead of verifying. `.stignore` (`(?d)tmp*.tmp`, the temp name `fsutil.py` and `storage/local.py` create) is written first, keeps any other bytes, and is a no-op when the line exists; a leftover one never blocks a rerun. `_write_stignore` calls `fsutil.refuse_real_state_write_under_pytest` before its first mutation. Entry names in messages go through `safety.safe_terminal_str`.

Plain `mm init` first checks for saved join answers (`_load_join_record_or_stop`, `~/.config/mind-meld/join.toml`) and asks `Continue joining? [y/n] (Enter = y)`, or asks whether to start a new fleet or join an existing one (`_ask_start_or_join`, rendering `Start a new fleet or join an existing one? [n/j]` and accepting `n`/`new` or `j`/`join`. Enter asks again. `new` takes the `--new-fleet` path; `--new-fleet` skips both questions). On a configured machine an interactive `new` answer also requires the new-fleet overwrite confirmation, which names the current storage path and key fingerprint if available. Joining asks every join question except the passphrase first (storage path, fleet device ID on a managed join when pairing is needed, device name, sources, and the applicable memory-setup questions), saves those answers in `join.toml` (never the passphrase), pairs and waits up to `APPROVAL_WAIT_SECONDS` for the fleet machine's approval when managed, accepts the folder offer, and probes/waits for `mm-crypto-init`. A fetch that remains `missing` after the managed wait below (or the first fetch when no wait applies: absent folder, bookkeeping only, blobs or manifests without a header, mid-delivery) exits 1 and creates no Mind Meld storage folder, `config.toml`, device entry, keyring item, key header or `.stignore`; the message mentions `--new-fleet` only when `--new-fleet` would accept the folder. There is no override: the typed `BRICK` confirm is gone. A present header is followed by `_init_storage_guard` (which asks only when the machine already has a device entry), unique short device ID generation, the passphrase prompt and verification (`_verify_join`), `.stignore` (when managed), device registration and `config.toml` save (`_register_and_save`), best-effort encrypted Syncthing record publication (`_publish_syncthing_record_best_effort`, writing `syncthing/<mm-id>.enc`), and best-effort removal of `join.toml` (`_forget_join_record`). Before returning the verified passphrase, `initflow.init` passes it and the memory-setup finalizer to the `pull_join` callback supplied by `cli.init`. That callback forwards the passphrase to `cli._attended_pull`, so a stale or unreadable keyring entry cannot fail the join's own pull. `initflow` never imports `pullflow`. A failed pull keeps config and device and ends with pull's one-line remedy. `--new-fleet` (and an interactive `new` answer) also publishes `syncthing/<mm-id>.enc`, deletes any leftover `join.toml` on completion, returns `None`, and does not pull. A closed or non-terminal stdin ends in the `mm init needs a terminal` error (`cli.init`), not `Aborted.`.

A crypto session on a folder with no header (`core._init_crypto_session`) says to wait for the folder to finish syncing, to restore the file from another machine if it never arrives, and never to reinitialize. It names no sync tool, includes the storage path, and does not contain `mm init`, so `_sync_failure` ends with `Run: mm diag`. The corrupt-header messages use the same wording.

## Syncthing setup in init (Track 118A, load-bearing)

`initflow.init` calls `_check_syncthing()` immediately after the overwrite confirm and the `Mind Meld v… — init` banner, before reading `join.toml` or asking any init question. `_check_syncthing()` sends only GET requests and writes nothing. It calls `config.load_syncthing_record()` (`~/.config/mind-meld/syncthing.toml`, `[syncthing] managed_device_id`, derived from `config.CONFIG_PATH` at call time and written via `save_config`) and `syncthing.classify_config(sanitize=safe_terminal_str)`:

| Result | Outcome |
|---|---|
| `reach` is `not-found` or `unreachable` | stop (exit 1): Syncthing is not running; nothing was written; `Run: <start command>` (`brew services start syncthing` on `darwin`, `systemctl --user enable --now syncthing.service` otherwise) |
| `reach == "ok"`, `source == "rest"`, record equals `local_device_id` | managed (`ManagedRecord(device_id=recorded_id)`), `persisted=True` (mm's own earlier writes make the configuration read as pre-existing on a rerun) |
| `reach == "ok"`, `source == "rest"`, `state == "default"`, no matching record | managed via `check.managed_record()`, `persisted=False` |
| `reach == "ok"`, `state == "pre-existing"`, no matching record (including a stale record for another Syncthing device) | owner-managed (`record=None`). Report the applicable reasons (another configured device, a non-default folder, or a shared or non-empty Default Folder) and point to README "Configuring Syncthing yourself". |
| `reach == "address-unsupported"` and offline `state == "pre-existing"` | owner-managed (`record=None`), same line |
| anything else (`unknown`, `unauthorized`, `error`, `config-unreadable`, offline default behind an unsupported address) | stop (exit 1): `init: could not read Syncthing's configuration (<reach>/<cause>)... Nothing was written. Run: mm diag` |
| `load_syncthing_record` raises `ConfigError` | stop (exit 1) with its message plus `Nothing was written. Fix or remove that file, then run 'mm init' again.` |

**Order of writes:**
- **Managed `--new-fleet` (or interactive `new`):** check (GET only) → storage path → folder/header reads → device name (`_default_device_name`: on `sys.platform == "darwin"`, runs `scutil --get LocalHostName` with a 2 s timeout and uses the first stdout line after stripping whitespace if the command succeeds and that line is nonempty, falling back to `socket.gethostname()`) and passphrase → readable Syncthing state and local-only existing-folder check → record (`save_syncthing_record`) → own Syncthing device name (`set_own_device_name(device_name)`) → Default Folder removal (`remove_default_folder`, nested inside `stock_default_folder_path()` only) → mm's folder (`create_folder("mind-meld", "Mind Meld", full_path)`) → `.stignore` → key header (`mm-crypto-init`) → sources → memory-setup questions (`_ask_memory_setup(None)`) → device entry → `config.toml` → keyring → best-effort `syncthing/<mm-id>.enc` publication (`_publish_syncthing_record_best_effort`) → best-effort `delete_join_record` (`_forget_join_record`) → best-effort memory-index refresh (`_refresh_memory_index_best_effort`, notice-not-failure) and pointer-line apply (`_apply_pointer_line`, warning-not-failure per file) → prints this machine's Syncthing device ID.
- **Managed join (`mm init`):** check (GET only) → load `join.toml` (`_load_join_record_or_stop`; if present, show saved answers and confirm `Continue joining?`, or `_forget_join_record` and ask `_ask_start_or_join`) → storage path (from record or prompt) → folder read → `_managed_folder_ready` (when `syncthing.read_state(full_path)` already reports `state == "ok"`, `folder_id == "mind-meld"` and `folder_path == full_path.expanduser().resolve()` with valid `FOLDER_OPTIONS`, no pairing is needed; otherwise validate the saved fleet device ID against the local device or prompt via `_read_fleet_device_id`) → device name (`_default_device_name`) and sources (from record via `_sources_from_names` or prompt via `_prompt_sources`, refusing before any write if no user-facing sources are enabled) → memory-setup questions (`_ask_memory_setup(saved)`, reusing any non-`None` saved answers and asking only unasked ones) → when pairing is needed, `_require_shareable_folder` (require absent/empty or bookkeeping-only before any record or REST write) → save `join.toml` for a new join, a newly entered fleet device ID, or newly filled memory answers (`_save_join_record_or_stop`) → when pairing is needed, `_managed_join(setup, full_path, fleet_id, device_name)`: record (`save_syncthing_record`) → own Syncthing device name (`set_own_device_name(device_name)`, before `add_device` so the fleet first sees that name) → `add_device` → prints own device ID and copyable `mm devices approve <local_id>` line → Default Folder removal (nested only) → `accept_folder_offer`, polling up to `APPROVAL_WAIT_SECONDS // APPROVAL_POLL_SECONDS` rounds (300 × 2 s) on `refused`/`no-offer` under `core._installer_progress` and exiting 1 via `_stop_waiting` on timeout or Ctrl-C → folder re-read → header probe (`_fetch_header_or_stop`; when `accepted_share is True` and `missing`, `_wait_for_header` polls up to `HEADER_WAIT_SECONDS` at `HEADER_POLL_SECONDS` intervals under `core._installer_progress`, exiting 1 via `_stop_waiting` on Ctrl-C; if still `missing`, re-classify folder: bookkeeping-only or in-flight exits 1 via `_stop_waiting`, fleet/other or unreadable uses `_stop_for_missing_header` / `_unreadable_folder`) → re-init guard (`_init_storage_guard`) → unique short device ID → passphrase prompt and verify (`_verify_join`) → `.stignore` (`_write_stignore`) → device entry → `config.toml` → keyring → best-effort `syncthing/<mm-id>.enc` publication (`_publish_syncthing_record_best_effort`) → `_forget_join_record` → pull → best-effort memory-index refresh (`_refresh_memory_index_best_effort`, notice on failure) and pointer-line apply (`_apply_pointer_line`, warning per failed file) (`cli._attended_pull`).
- **Owner-managed (`setup.record is None`):** check → guide line → load `join.toml` / `Continue joining?` or `_ask_start_or_join` → storage path → folder read → (on join: device name, sources, and `_ask_memory_setup(saved)`, no fleet device ID prompt, save `join.toml` when new or when previously unasked memory answers were filled) → header probe → re-init guard → short device ID → passphrase → verify → device entry → `config.toml` → keyring → best-effort `syncthing/<mm-id>.enc` publication when `setup.local_id` is present (`_publish_syncthing_record_best_effort`) → `_forget_join_record` → pull → best-effort memory-index refresh (`_refresh_memory_index_best_effort`, notice on failure) and pointer-line apply (`_apply_pointer_line`, warning per failed file).
- **Own and peer Syncthing device-name rule (Tracks 153A, 154A, SPEC O2.6 boundary):** `SyncthingWriter.set_own_device_name(name)` is called only by `initflow._managed_new_fleet_folder`, `initflow._managed_join`, and `meshflow._run_inner` (pinned by `tests/test_syncthing_write.py::test_set_own_device_name_referenced_only_by_managed_setup_paths`), and `SyncthingWriter.set_device_name(device_id, name)` is called only by `meshflow._run_inner` (pinned by `tests/test_devices_approve.py::test_no_push_pull_or_auto_command_ever_accepts_a_device`). Both refuse a non-string or whitespace-only name with `bad-device-name` before any request, recheck `GET /rest/config/devices` after `_begin()`, return `unchanged` on an exact name match, and send `PATCH /rest/config/devices/{id}` with `{"name": name}` when the name differs. During `meshflow.run`, a failure on either name write records a degradation naming the web-UI step without failing the sync command.

Managed setup stops before writes when `syncthing.read_state` cannot establish the current folder state. Managed `--new-fleet` refuses an exact existing target whose peer count is nonzero or unknown, so an accepted share waiting for delivery cannot be re-keyed; local-only failed-bootstrap retries remain valid. A plain join on a local-only bookkeeping-only folder without a header points back to `mm init --new-fleet`; a present header still follows normal join verification. Folder-exists and path-overlap refusals direct the owner to reconcile folder paths/options/sharing in Syncthing's GUI before rerunning the original command.

A newly shared managed join target must be empty or contain only `_BOOKKEEPING_NAMES` (`_require_shareable_folder`); plaintext, another fleet, and in-flight files all stop before `join.toml`, `syncthing.toml` or REST mutations. An already configured `mind-meld` folder at the exact resolved target (`_managed_folder_ready`) skips this guard, so delivered fleet content remains joinable on reruns. Recheck a new target immediately before the first offer attempt and after every approval poll delay. If files arrive during the wait, stop before sharing the folder and keep the saved answers. All joins refuse a storage path that includes the local Mind Meld config directory.

An exact-folder managed join retry still validates every `FOLDER_OPTIONS` value through `option_is_ok`; invalid or missing options stop with the existing GUI reconciliation remedy before further prompts or writes. Missing `.stignore` remains allowed because the verified join installs it later.

If a saved join now needs pairing and has no fleet device ID, check the target with `_require_shareable_folder` before prompting for the ID.

When `accepted_share is True` (either `_managed_join` just accepted the `mind-meld` folder offer or `syncthing.read_state` reported the exact `mind-meld` folder already shared with `peer_count >= 1`) and the initial `_fetch_header_or_stop` returns `missing`, `_wait_for_header` prints `Waiting up to 2 minutes for Syncthing to deliver the key header (mm-crypto-init); Ctrl-C stops the wait without writing Mind Meld data.` and polls `_fetch_header_or_stop` up to `HEADER_WAIT_SECONDS // HEADER_POLL_SECONDS` times (120 × 1 s via `_pause`; Track 127A) under `core._installer_progress("Waiting for the key header")`. It never waits when `accepted_share is False` (a local-only `mind-meld` folder with 0 peers) or `accepted_share is None` (owner-managed Syncthing, or a managed exact-folder rerun whose `total_peers` is unknown). If the header arrives during the wait, `init` continues in the same run; if a corrupt or newer-format header arrives, `_fetch_header_or_stop` stops immediately with its existing message. If it is still `missing` after the wait, `init` re-classifies `full_path`: when the folder is readable and holds only bookkeeping or in-flight names (`not folder.fleet and not folder.other`), it exits 1 via `_stop_waiting` with the header waiting outcome; when the folder is unreadable or holds `fleet` or `other` files, it stops through `_unreadable_folder` or `_stop_for_missing_header(..., local_only=False)`. Ctrl-C during `_wait_for_header` catches `KeyboardInterrupt` outside the spinner's `with` block and exits 1 via `_stop_waiting` with the same header waiting outcome. Both the post-wait missing-header stop and the Ctrl-C stop follow `join.toml`, Syncthing writes and `syncthing.toml`, and write no mm storage folder, `config.toml`, device entry, keyring item, key header (`mm-crypto-init`) or `.stignore`.

The join tail refreshes the index once after the initial pull attempt so it sees incoming memory. When delivery is incomplete or the pull fails, Claude's approved edit still runs and init prints the line for manual addition to synced Codex instructions once the files arrive. A failed index refresh or an instruction-file write failure preserves the command outcome.

**Pytest default stub:** `tests/conftest.py` defines an autouse fixture `_default_init_syncthing` that patches `initflow._check_syncthing` to return a silent owner-managed `_SyncthingSetup(record=None, local_id=None, persisted=False)`. Opt out in a test by requesting the `fake_syncthing` fixture or the no-op `real_syncthing_gate` fixture.

## Join record, approval wait and introductions (Track 151A, load-bearing)

- **Join record (`~/.config/mind-meld/join.toml`):** `config.JoinRecord(storage_path, fleet_device_id, device_name, sources, memory_index=None, embeddings=None, pointer_line=None)` is written through `config.save_join_record` → `save_config(..., join_record_path())` (atomic, fsynced, mode `0600`, guarded by `fsutil.refuse_real_state_write_under_pytest`). `join_record_path()` derives `CONFIG_PATH.parent / "join.toml"` at call time. `[join]` stores `storage_path` (tilde form preserved, a relative path made absolute before saving; `config.toml`'s `storage.path` follows the same rule in every mode — join, interactive `new` and `--new-fleet` — because `config.load_config` resolves the saved path against the working directory), `fleet_device_id` (canonical Syncthing device ID, omitted when `None` on owner-managed or already-configured-folder joins), `device_name`, `sources` (non-empty list of enabled user-facing `DEFAULT_SOURCES` names, excluding `MM_INTERNAL_SOURCE_NAMES`), and optional tri-state booleans `memory_index`, `embeddings`, and `pointer_line` (each omitted when `None`, so pre-change records load with all three as `None` and a resumed run asks only the unasked ones before waiting and re-saves). **The passphrase is never passed to `save_join_record` and never written to `join.toml`.**
- **Pytest memory-setup stub:** `tests/conftest.py` defines an autouse fixture `_default_init_memory_setup` that patches `initflow._ask_memory_setup` to return `(None, None, None)` unless a test requests the `real_memory_setup_gate` fixture, keeping all existing init stdin sequences host-independent.
- **Reader and lifecycle:** the only reader of `join.toml` is the resume path in `initflow.init` (`_load_join_record_or_stop`). On a plain `mm init` run (without `--new-fleet`), a present valid record prints `  Saved join answers: storage <path>, [fleet machine <id>, ]device name <name>, sources <a, b>.` (values sanitized with `safe_str`) and asks `Continue joining?` (`default=True`). When the record carries memory answers, the summary includes them. A saved pointer-line yes shows the current target paths before confirmation. Answering yes reuses those answers (rebuilding `sources` in `DEFAULT_SOURCES` order with `MM_INTERNAL_SOURCE_NAMES` auto-included via `_sources_from_names`) and asks for the passphrase and any applicable re-init confirmation. If a managed join now needs pairing and the record lacks a fleet ID, prompt for it and save it before pairing. Answering no calls `_forget_join_record(required=True)` (`config.delete_join_record()`, which guards with `fsutil.refuse_real_state_write_under_pytest` before `unlink(missing_ok=True)`), sends nothing to Syncthing, and starts over at `_ask_start_or_join()` after removal succeeds. If removal fails, stop and name the file to remove. Every completed `init` (join, interactive `new`, or `--new-fleet`) calls `_forget_join_record()` after `_register_and_save` succeeds; an `OSError` during cleanup emits a `core._warning` naming the file and instructing the owner to delete it by hand without changing the exit code. A declined `_init_storage_guard` leaves `join.toml` in place for the next run. A malformed or unreadable `join.toml` raises `ConfigError("config: <path> is not a valid join record (<why>).")` and `_load_join_record_or_stop` exits 1 with `Nothing was written. Fix or remove that file, then run 'mm init' again.` and `Run: mm init` before any join prompt or non-GET request.
- **Approval wait inside `_managed_join`:** `APPROVAL_WAIT_SECONDS = 600` (about 10 minutes) and `APPROVAL_POLL_SECONDS = 2`. After `add_device`, `_managed_join` prints its Syncthing ID and short ID, followed by short-ID and full-ID approval commands on separate copyable lines, removes the unshared empty stock Default Folder when nested, and calls `writer.accept_folder_offer(...)`. When the initial result is `refused`/`no-offer`, it prints `  Waiting up to 10 minutes for that approval; Ctrl-C stops the wait and keeps your answers.` and polls `writer.accept_folder_offer(...)` up to `APPROVAL_WAIT_SECONDS // APPROVAL_POLL_SECONDS` rounds (`_pause(APPROVAL_POLL_SECONDS)` per round, under `core._installer_progress("Waiting for the fleet machine's approval")`). The poll loop lives inside `initflow._managed_join` so every `SyncthingWriter` pairing-method reference remains inside `devicesflow.approve`, `initflow._managed_join` and `meshflow` (`tests/test_devices_approve.py::test_no_push_pull_or_auto_command_ever_accepts_a_device`). Any outcome other than `refused`/`no-offer` exits the loop and passes through `_require_syncthing`.
  The 600-second budget counts the pauses. Folder rechecks and local Syncthing requests add to the elapsed wait.
- **Waiting outcome (`_stop_waiting`):** both an approval-wait timeout or Ctrl-C (`what = "a fleet machine to approve this one ('mm devices approve <id>')"`) and a header-wait timeout (when the folder is readable and holds only bookkeeping or in-flight files) or Ctrl-C (`what = "Syncthing to deliver the fleet's key header (mm-crypto-init) to <path>"`) call `_stop_waiting(what)`, which prints one stdout outcome line (`Init: waiting for <what>; your answers are saved, and no device entry, config or key header was written. Run: mm init`) via `core._print_outcome` and exits 1 (`raise typer.Exit(1)`).
- **Why the introducer mark yields no introductions at join time (Track 151A finding; historical rationale for Track 170A):** Track 170A removed mutual introducer flags to stop Syncthing warnings. The joiner now initiates connections to other authenticated fleet peers on its first pull, replacing the first connection that the approver's introduction formerly initiated. In Syncthing v2.1.7 (`lib/model/model.go`), `ClusterConfig` applies an introducer's device list only in `handleIntroductions`, which skips any folder this machine does not yet have configured or does not share with the introducer (`"Don't have this folder, carry on."` / `"not shared with the introducer"`). Syncthing sends `ClusterConfig` only when a peer connection starts, at startup, or in `CommitConfiguration` when the announcing machine's own folder/device configuration changes; changing a device's `introducer` flag triggers no message (the device loop in `CommitConfiguration` reacts only to `Paused`, `IgnoredFolders`, and rate limits). During a managed join, the joiner marks the fleet machine as introducer before approval and creates/accepts the `mind-meld` folder only *after* receiving the fleet machine's approval announcement, and the joiner's own folder creation makes the joiner announce to the fleet machine rather than making the fleet machine re-announce to the joiner. Consequently, the joiner learns no other fleet device from the introducer until its next reconnection to the introducer (a Syncthing restart or network change) or the introducer's next configuration change; meanwhile, other fleet machines that already shared `mind-meld` with the introducer learn of the joiner immediately when the introducer approves it and appear on the joiner as pending devices. Verified against Syncthing v2.1.7's source and a live three-instance loopback probe (introducer `SKVYK6N`, joiner `KSIPX43`, third fleet member `3HIQSA2`: 60 s after `KSIPX43` accepted `mind-meld`, `KSIPX43`'s `/rest/config/devices` held only `KSIPX43` and `SKVYK6N` while `3HIQSA2` had `KSIPX43` with `introducedBy: SKVYK6N` and `KSIPX43` listed `3HIQSA2` in `/rest/cluster/pending/devices`; pausing and resuming `SKVYK6N` on `KSIPX43` immediately added `3HIQSA2` to `KSIPX43`'s `/rest/config/devices` with `introducedBy: SKVYK6N`). Marking the introducer later would not trigger an announcement, and mm does not force a pause/resume reconnect because an interrupted reconnect would leave the fleet device paused; instead, mm leaves full fleet mesh convergence to SPEC O2.3's encrypted-store mesh step (Track 152A).
- **Which name a peer stores for an empty-named new device and for an introduced device (Track 153A finding, verified in Syncthing v2.1.7 source; unverified against live Syncthing):** in `lib/connections/service.go` (`helloForDevice`), a machine that already knows the connecting peer populates `hello.DeviceName` from its own configured device entry (`myCfg.Name` in `/rest/config/devices`). See [the v2.1.7 hello handshake](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/connections/service.go#L280-L294) and [connection name handling](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/model/model.go#L2171-L2182). ## Init order + push-time self-heal (load-bearing, v0.9.4)
`_register_and_save` (renamed from `_save_and_register`) writes the remote first, the local pointer last: `register_device(backend, ...)` → `save_config(...)` → keyring store. Canonical filesystem/DB transaction discipline — a SIGKILL/OOM/power-loss in the window between the two writes leaves an inert orphan storage entry (recoverable on retry with plain `mm init`; the orphan-case prompt applies only when local config already has a device ID), never the inverse half-state where local config claims a `device_id` storage doesn't contain. Pre-v0.9.4 produced the inverse mapping. Do NOT reorder these calls.

If `save_config` raises (disk full, permissions), a best-effort `backend.delete(device_key(device_id))` cleanup runs before the original exception propagates — keeps orphans from accumulating in storage when normal save failures hit. Cleanup-failure surfaces a `mm: warning:` stderr breadcrumb but does NOT mask the original save error (visible-failure contract). The `device_key(device_id)` storage key is precomputed BEFORE `register_device` so the cleanup-warning f-string can't itself raise from `device_key`'s validation and mask the real cause (codex adversarial 2026-04-25).

**Known limit: a save failure can follow publication.** `save_config` writes through `atomic_write_bytes(fsync=True)`, whose parent-directory flush runs after `os.replace`. That flush can raise with config.toml already naming the new `device_id`, and the handler above cannot tell it from a pre-publication failure, so it still deletes the registration. Reproduced, not repaired; its repair card ("Preserve coherent state after config publication failures", drained from the TODOS entry "Init deletes device registration after a published config save fails") was killed on 2026-10-15: see [sync.md "Atomic write publication failures"](sync.md#atomic-write-publication-failures). Whether a later push's `_ensure_device_registered` self-heal fully recovers is unqualified. Preserve the pre-publication cleanup when repairing.

`_ensure_device_registered(backend, device_id, device_name, *, dry_run)` runs at the top of `_push_core` BEFORE any push work. If `devices/<my_id>.json` is absent, it recreates it via `register_device`. Two scenarios converge: future v0.9.4+ SIGKILL crash mid-init (cosmetic) AND retroactive fix for pre-v0.9.4 victims of the v0.8.15..v0.9.3 inverted half-state — those users had been pushing manifests under an ID no peer recognized, silently. First push after upgrading to v0.9.4 self-heals. Gated on `not dry_run` (codex review: `mm push --dry-run` must not mutate storage). Register failures emit a `mm: warning:` stderr breadcrumb before re-raising — load-bearing for autopush, whose generic `except Exception` would otherwise swallow the failure and silently no-op every push.

## Device table and storage names (Track 87A)
A file in `devices/` is a device only when its name is that device's key: `devices/<id>.json` whose body holds `device_id == <id>` (`keys.parse_device_key`). Everything else is foreign and never refuses a pull: conflict copies (iCloud, Dropbox, Syncthing), misnamed files, a body whose id is not its file name. ## `register_device` create-only contract (load-bearing, v0.10.1)
Pre-v0.10.1, `register_device` always wrote `backend.put(key, ...)`. The push-time `_ensure_device_registered` self-heal (v0.9.4) called `register_device` whenever `backend.exists(key)` returned False. iCloud's `.icloud` placeholder (cloud-only, lazy-materialized) creates a TOCTOU window where `backend.exists()` reports False but the entry actually exists on storage — the self-heal re-registered, silently bumping the `registered:` first-registration timestamp on every push.

v0.10.1 routes `register_device` through `LocalBackend.put_exclusive(key, data)` (atomic `os.link` with `EEXIST` detection) so the create-only invariant holds at the filesystem layer regardless of placeholder state. Existing entries surface as `StorageError`, which the function swallows + returns. Original `registered:` timestamps are preserved across re-registration. Idempotent: self-heal callers can re-register safely.

## Devices write lock (load-bearing, v0.10.1)
`update_last_seen` does a read-modify-write of `devices/<id>.json` on every push (mutates `last_seen` + `last_seen_version`). Concurrent autopush + interactive push could race on the RMW. Today's deterministic fields (`last_seen`, `last_seen_version`) don't lose data because both writers compute the same effective state, but any FUTURE non-deterministic field (e.g. per-machine notes, error counters, partial-progress markers) would lose interleaved updates.

`_devices_write_lock()` is a `contextlib.contextmanager` wrapping the RMW in `fcntl.LOCK_EX | LOCK_NB` against `~/.config/mind-meld/devices-write.lock` (mode 0o600, parent dir auto-created). Brief retry budget on contention — `_LOCK_RETRY_INTERVALS_S = (0.05, 0.1, 0.2, 0.4)` (~750ms total before degrading). Total acquire wait stays well under 1 second since the critical section is one storage GET + one storage PUT.

On exhausted retries, degrade to executing without the lock and emit one `mm: warning: device write lock contended; skipping last_seen update for this push` line to stderr (visible-failure contract). Today's deterministic fields are safe under degraded operation; the warning lets the user catch a stuck-process scenario before any future non-deterministic field starts losing data.

The lock is LOCAL (per-machine config dir) — `fcntl.flock` is a local-process primitive and never reaches synced storage. All RMW callers MUST hold the flock for the read AND write so an interleaved read can't observe a partial state. Routing field-adders through this lock is forward-defense for concurrency safety.

## Peer-controlled string sanitization (load-bearing, v0.10.1, security)
Every synced filename AND file body crosses an untrusted trust boundary. Without sanitization, a peer can plant Rich markup (`[/red]…[red]`) or terminal escape sequences in any synced filename or file body and have them rendered as control output during `mm pull` / `mm conflicts` / `mm resolve` / `mm devices` / `mm status`. The OSC 52 vector is particularly nasty — many terminals (xterm, iTerm2, kitty, alacritty) honor base64-encoded clipboard writes from remote-controlled escape sequences, silently changing the user's clipboard. CSI `\x1b[2J` clears the screen; OSC 0/2 spoofs the title; DCS / C1 8-bit are also covered.

`_strip_terminal_grammar` (private) removes the full common-grammar set: CSI `\x1b[…[\x40-\x7e]`, OSC `\x1b]…(BEL|ST)`, DCS, single-byte `\x1b[\x40-\x5f]` (SS2/SS3 and other C1-index finals; RIS `ESC c` is not in that range), and the rarely-used 0x9b 8-bit C1 CSI variant. That intermediate is not safe to render: one regex pass can assemble a fresh OSC by deleting an inner CSI.

Public `strip_terminal_escapes(s)` runs the grammar helper, then deletes every residual ESC (`U+001B`) and C1 (`U+0080`–`U+009F`). Returned text is ESC/C1-free. This is not an all-control guarantee: LF and HT survive (required for `safe_text` diff bodies), and other C0/DEL/Unicode-format characters are left to the sink. Apply BEFORE rendering any peer-controlled string to a real terminal — Rich's `Text()` does NOT strip these.

`safe_str(s)` composes public `strip_terminal_escapes` with `rich.markup.escape` and returns a plain `str`, so f-string composition with Rich markup tags continues to work: `f"[red]write failed:[/red] {safe_str(rel_path)}"`. Use at Rich markup print sites interpolating a peer-controlled string (filenames, paths, source names, device names, error message tails — including exceptions whose `str(e)` echoes peer-supplied bytes).

`safe_terminal_str(value)` is the helper for single-line plain stderr (Track 50A, v0.14.4; Track 52A, v0.14.6, keeps its visible notation). It stringifies, runs the private grammar helper (not the public residual-deletion path), then keeps each remaining character only if `str.isprintable()` is true; otherwise it renders `ascii(ch)[1:-1]`. That visibly escapes residual C0/DEL/C1, Unicode line separators, format controls (including ZWJ, so some joined emoji spellings appear split), and surrogate codepoints, while preserving printable Unicode and literal brackets. Residual ESC/C1 therefore appear as printable ASCII notation, which already satisfies the forbidden-codepoint property. Display text is not a filesystem identity or a shell argument — callers keep the original Path / storage key / model id for validation, lookup, recovery, and deletion. Rejected storage-filename warnings in `LocalBackend.find_conflict_copies` use this helper directly; the malformed-blob and verbose-orphan GC warnings compose `safe_str(safe_terminal_str(bkey))` because those sinks are Rich markup. Original storage keys are still used for parse, lookup, and deletion. Track 52A also routes the token-cache GC failure notice, the oversize-jsonl-line notice, and the unknown-model pricing notice through this helper; remaining plain-stderr `safe_str` sites are a recorded follow-up.

`safe_text(s, **kwargs) -> rich.text.Text` is the diff-content variant. Use for diff CONTENT lines (peer-controlled file bytes printed via `console.print`). `Text()` alone defangs Rich markup but passes raw ANSI/OSC/DCS through to the terminal. It calls public `strip_terminal_escapes` first, then forwards `**kwargs` to `Text()`. `Text.plain` is ESC/C1-free; LF and HT remain exact. Caller-supplied Rich styles/kwargs are trusted application formatting.

Sweep covers ~30 print sites: pull-prediction widget, upload progress, conflict prompts, write/merge/conflict apply paths, all `_apply_*` / `_pull_*` error tails, `mm devices` table cells, `mm diff` per-source headers, fleet-version refusal listing, `_print_pull_summary` warnings, `_resolve_interactive_loop` headers + prompts + diff labels + diff content + outcome lines. `mm devices` Rich Table cells are sanitized too — Table cells interpret markup AND pass raw escapes through (verified). All sites pinned in `tests/test_safe_str.py`.

**v0.11.1 extension — banner trust boundary covers `device_name` too.** The conflict-prompt LOCAL/REMOTE banners (Track 12A, conflictdiff.py) interpolate two peer-controlled strings: the conflict filename AND the peer's `device_name` (set via `typer.prompt` at peer init, plaintext-synced via `devices/<id>.json`, and rendered as `(from <peer_name>)` on the REMOTE banner). `render_banner` wraps both inputs in `safe_text` BEFORE composition so a peer planting OSC 52 / CSI / DCS in their own `device_name` cannot reach the terminal of any peer that pulls. Codex outside-voice review (T6) caught this — pre-v0.11.1 the sanitization sweep covered filenames but not `device_name`. Pinned by `tests/test_safe_str.py::TestConflictBannerSanitization`.

**v0.11.1 module move.** `safe_str`, `safe_text`, `strip_terminal_escapes` live in `mind_meld.safety` (extracted from cli.py to break the cli↔conflictdiff circular import). `cli.py` imports only `safe_str` and `strip_terminal_escapes` for its own call sites without compatibility re-exports; tests import from `mind_meld.safety` directly.

## `store_passphrase_in_keyring` PYTEST_CURRENT_TEST guard (load-bearing, v0.11.11)

## Non-interactive keyring reads (Track 73A)

`crypto.get_passphrase(non_interactive=True)` is the hook path
(`autopull`/`autopush`). On keyring's Secret Service backend it must never
send `Unlock`, `Prompt` or `CreateCollection` and never call
`keyring.get_password`: keyring's own read unlocks a locked collection and
creates a missing default one, and secretstorage waits on that desktop
dialog with no timeout, so an agent hook would hang. `_read_secret_service`
reads the collection directly through secretstorage instead: open the
member's preferred (else default-alias) collection, raise
`KeyringUnavailableError("no-default-collection", "secret-service")` when it
does not exist, `("locked", ...)` when it is locked or the item read reports
locked (`LockedException`, or a D-Bus error named
`org.freedesktop.Secret.Error.IsLocked`), else first-match `search_items` +
`get_secret` in keyring's configured scheme. The attended (interactive) path
is unchanged and may still raise a desktop unlock prompt.

**Chainer walk rules.** `_non_interactive_keyring_read` walks
`ChainerBackend.backends` read exactly once (it recomputes discovery per
access), in keyring's priority order; a non-chainer backend walks as a
single member. A value ends the walk. A member yielding no value — `None`,
or a `KeyringError` from the family `get_passphrase` has always swallowed —
moves to the next member. `KeyringUnavailableError` (locked /
no-default-collection from a Secret Service member, `denied` below) stops
the walk and propagates. Every other exception propagates (v0.8.9
narrow-catch contract). Any `keyring.errors.KeyringLocked` from a
non-Secret-Service member becomes `keyring-locked` downstream:
`KeyringUnavailableError("denied", "keychain")` when the member's class
module starts with `keyring.backends.macOS` (string check, so Linux never
imports that backend), else `("denied", "other")`.

**Env fallback and connect parity.** `MINDMELD_PASSPHRASE` is used whenever
the keyring cannot answer without prompting: on `KeyringUnavailableError`
the env value wins if set, else the error reaches `_auto_command_setup`'s
skip arm. Connect errors keep exact parity with keyring: `dbus_init`
failures propagate untouched (keyring calls it outside its `InitError`
wrapper, so the outcome stays `keyring-error`), while a non-`ItemNotFound`
`SecretStorageException` from opening the collection is treated like
keyring's swallowed `InitError` — the member yields no value. Errors from
`is_locked()` and from the item read (other D-Bus errors, `OSError`,
`UnicodeDecodeError`) propagate. An empty-string secret is returned as is,
matching keyring.

**Stored-item contract.** The reader finds the passphrase by keyring's
configured scheme (`member.schemes[member.scheme]`): default
`service=mind-meld`, `username=passphrase`; KeePassXC scheme
`Title=mind-meld`, `UserName=passphrase`. Writers must keep storing under
that scheme — `store_passphrase_in_keyring` does so through keyring today.
A future Linux passphrase flow must keep this contract or update the
reader with it; the README's `secret-tool store` recovery command writes the
same attributes (plus keyring's `application` attribute).

The `secretstorage>=3.4` floor exists because only 3.4+ maps a missing
collection's D-Bus `UnknownObject` reply to `ItemNotFoundException`; 3.3.x
raised a raw D-Bus error, which surfaced as `keyring-error` instead of
`keyring-no-collection`.

**Diag probe.** `crypto._secret_service_state()` reports module-qualified
backend/member class paths (`_backend_label`; every keyring backend class is
named `Keyring`, so bare names identify nothing) and closed-vocabulary
`secret_service` / `item` states for `mm diag` (`keyring` key); `backend` is
`unavailable` without the keyring package and `unknown` when discovery
raises. It never reads a secret (`search_items` only,
for presence), never prompts, and degrades any exception to
`unknown` + the exception class name. `statusflow.py` calls it module-qualified
(`crypto._secret_service_state()`) so test patches on the owner module
reach it.

**Residuals (accepted, not covered by the narrow read).** KWallet,
KeePassXC's own confirm-access dialogs, and keyring's libsecret backend can
still prompt inside `member.get_password`; macOS Keychain access dialogs
can still appear for attended reads (the auto path converts a denial, it
cannot pre-empt the dialog); a stalled D-Bus session can still block hooks
and `mm diag` (no timeout backstop — deferred, see TODOS). Attended
commands agents run (e.g. `mm status`) still read interactively first.

## Verified crypto repair and read-only inspection (Tracks 56A/60A)

### Newer format refusal (Track 66A, v1.0.0)

`crypto.FORMAT_VERSION_MAX` reserves 0x03–0x0F: crypto-init and blob readers
refuse that window as newer, and the next such format takes 0x04. Read the version byte before assuming a layout, even on a one-byte
envelope. A current-format init with a keycheck in that window is newer too.
Empty/truncated v2 and bytes above 0x0F remain corrupt; a valid conflict copy
can still be selected beside ASCII garbage, but cleanup never rewrites canonical.
If **any** observed canonical or conflict copy is
newer, `fetch_crypto_init` returns `corrupt` with `newer_version` set, no winner
and no repair plan. Every crypto session refuses. Status reports the refusal;
diag remains an inspection and exposes `crypto_init.newer_version` (null when
none). Neither uses a newer copy's assumed salt or keycheck layout.

`apply_crypto_init_repair` re-fetches even with no pending plan; fresh newer
evidence raises `NewerFormatError` before anything is unlinked.
The CLI adds the single upgrade remedy using `upgrade.INSTALL_CMD`; crypto
never imports upgrade. Autorun keeps exit 0 and the `crypto-error` breadcrumb.
Newer blobs raise the same typed `CryptoError` subclass; per-file pull warnings
add the upgrade remedy. `_fetch_remote_manifest` and `_make_manifest_validator`
deliberately fold that subclass into corrupt-manifest handling. A manifest
copy whose first byte is in 0x04–0x0F is unreadable even when an older sibling
still decrypts, and a newer conflict copy is not "missing". A read that sees
that byte after the preliminary scan, including the conflict validator's own
read, still returns corrupt instead of using the older sibling. Pull skips
that peer; GC refuses only for its own manifest, when it is unreadable or held
only by conflict copies. Push re-fetches
immediately before publication, and GC revalidates its own manifest immediately
before blob candidate listing/deletion. Manifest recovery also refuses
before replacing this Mac's own newer manifest. Blobs only the unread copy could name are kept.

Track 90A allocates 0x03 to **manifests** (shared Claude project names): a
manifest copy whose first byte is 0x03 is readable (`crypto.decrypt_manifest`),
0x04 to 0x0F are unreadable newer manifests (`crypto.newer_manifest_version`), and
blobs and `mm-crypto-init` keep treating 0x03 as a newer format. `mm-crypto-init`
is never written for it; see [Storage-format gates](auto-upgrade.md#storage-format-gates).

The folder's sync tool does not guarantee arrival order (`order = alphabetic`
in Syncthing only reduces waiting). A format-changing MAJOR must write its new
crypto-init **before** new-format manifests/blobs, and refuse on the newer side
while any registered peer runs below 1.0.0 (0.14.x lacks this gate). A manifest
or blob may still arrive first: pull skips an unreadable peer manifest with a
warning, GC refuses while its own manifest is unreadable or held only by conflict
copies, and push writes only its
own manifest. Init rescans immediately before bootstrap and again before
accepting a new salt, so a newer copy that arrives during the prompts refuses
without saving config. This is an optimistic local recheck, not a distributed transaction.
See [Storage-format gates](auto-upgrade.md#storage-format-gates).

plus valid older copy, byte-for-byte preservation and late arrival),
`TestNewerStorage66A` in `tests/test_integration.py` (command refusal, bootstrap

in `tests/test_diag.py`.

### Current-format reconciliation

`fetch_crypto_init(backend)` is pure; there is no `repair` parameter. It selects the lex-smallest-salt valid candidate (canonical first on ties), retains the exact winning bytes, and returns a frozen `CryptoInitRepairPlan`. Cleanup eligibility is separate from winner selection: the plan binds each conflict copy's name and content hash to `delete` only when canonical is readable and the copy is byte-identical to canonical, and to `preserve` for everything else (a different salt, memory parameters, keycheck or malformed content; an unreadable copy; any copy when canonical is missing or unreadable). A copy that holds the winner while canonical differs is therefore never removable. Canonical and conflict copies are read with `O_NOFOLLOW` as regular files; a symlink or other unreadable name has no digest authorizing removal. The plan has no `replace_canonical`, and `crypto_init_repair_counts` returns only `delete` and `preserve` over the conflict copies.

`_init_crypto_session` orders pure fetch → fingerprint drift check → load key → verify passphrase → `crypto.apply_crypto_init_repair` for mutating sessions. The repair function re-fetches and aborts with `CryptoError` when the exact winner changed, even if there was no pending repair, and when canonical's bytes differ from what the plan hashed. It **writes nothing**: no canonical write, no preserve file, no copy. It unlinks only `delete` copies, re-reading each name and canonical immediately before the unlink so a late replacement of either leaves every copy in place (pinned by `tests/test_crypto.py::TestConflictConvergence::test_concurrent_canonical_replacement_retains_conflict_copies`). A missing canonical removes nothing; two identical copies of a losing canonical both stay. Differing copies stay in place for the owner to move out of the folder by hand (README "Key header copies differ"). Names are re-listed and intersected with the plan, never joined from stored strings. Rechecking is optimistic local filesystem coordination, not a distributed transaction. Releases before Track 89A wrote `mm-crypto-init.preserved-*` files; this one never does, and they never match the conflict pattern.

The retro's historical-name reader checks the configured fleet fingerprint
before using the header and restores the previous crypto session afterward.
Targeted retirement lookups pass the requested device IDs to
`read_retirement_records` and use a confined, bounded read for those objects.

First-machine bootstrap remains create-only. Init's storage probe is pure; the join verifies before applying repair, and a changed winner aborts before config writes or device registration.

Inspection commands `status`, `diag`, and `diff`, plus `push --dry-run`, `pull --dry-run`, `gc --dry-run`, and `recapture --dry-run`, never repair shared crypto-init state. Status loads `_get_config(read_only=True)` and never persists a missing fingerprint; read-only crypto sessions backfill only in memory. Status and the previews print pending counts; diag reports `crypto_init.pending_repair` (`delete`, `preserve`), never copy names. Drift errors retain both fingerprints and put the stop sentence and the `'mm status'` pointer first, so `_sync_failure`'s 384-character cut keeps them with or without pending-cleanup text; the README anchor (`errors.KEY_HEADER_COPIES_URL`) closes the message and `mm status` prints it. They say to wait while copies sync, then stop if fingerprints still differ; never reinitialize or re-key. Pending conflict cleanup is explicitly qualified as not resolving this device's fingerprint mismatch, with no guaranteed recovery or fixed wait. The pending note mentions removal (and the next push, pull, autopull, or autopush that verifies the passphrase as its trigger) only when an identical copy exists, and says differing copies stay in place. Track 62A also gates their other setup writers; see the [README Previews table](../../README.md#previews). Every inspection loads config read-only, and declared status/identity-cache exceptions never permit shared crypto repair.
